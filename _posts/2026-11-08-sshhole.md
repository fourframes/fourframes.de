## SSHole (CVE-2026-123158): Authentication Bypass in OpenSSH im eigenen Lab nachgestellt

In den letzten Wochen folgte eine Schwachstellenmeldung der nächsten. Eine der jüngsten trägt den Namen SSHole und wurde am 05.11.2026 veröffentlicht: ein Authentication Bypass im OpenSSH-Daemon sshd, der als CVE-2026-123158 mit einem CVSS-Score von 8.1 eingestuft wurde.

### Warum die Schwachstelle selbst nachstellen?

Gefühlt blieb in letzter Zeit kaum Zeit, um jede einzelne Meldung zu validieren. Deshalb wurde nach der Veröffentlichung der Entschluss gefasst, diese Schwachstelle selbst nachzustellen und zu verstehen – einerseits, um den eigenen Horizont zu erweitern, andererseits, um zu prüfen, ob sie tatsächlich in der beschriebenen Form existiert. Mit der aktuellen Schlagzahl an Meldungen wäre es keine Überraschung, wenn sich demnächst eine Meldung wie ein Lauffeuer verbreitet, die sich bei näherem Hinsehen als gar keine Schwachstelle entpuppt. Links werden aktuell oft sehr schnell geteilt, gefühlt ohne vorher zu prüfen, ob das Beschriebene wirklich reproduzierbar ist.

### Das Setup

Die Schwachstelle betrifft Linux-Systeme, die die musl libc nutzen und deren sshd ohne PAM arbeitet – allen voran Alpine Linux, das sehr häufig als Basis für Docker-Images im Einsatz ist. Auch andere musl-basierte Systeme wie OpenWrt, Buildroot oder Yocto sind potenziell betroffen. 

Für die Nachstellung waren damit folgende Bedingungen nötig:

- Linux mit musl libc (hier: Alpine)
- sshd ohne PAM
- Passwort-Authentifizierung aktiviert (`PasswordAuthentication yes`)
- mindestens ein Konto, dessen Passwortfeld in `/etc/shadow` nur `*` enthält
- mindestens ein weiteres Konto mit einem `$5$`- oder `$6$`-Passwort-Hash

Für das Lab wurde folgendes minimales Dockerfile erstellt:

```dockerfile
# SSHole-Lab – absichtlich verwundbar, keinesfalls für Produktion nutzen
FROM alpine:3.15

# OpenSSH-Server installieren, Host-Keys erzeugen
RUN apk add --no-cache openssh-server \
 && ssh-keygen -A \
 # Konto mit echtem Passwort – dient später als Salt-Spender
 && adduser -D alice \
 && echo 'alice:correcthorse' | chpasswd -c sha512 \
 # Konto ohne Passwort, in /etc/shadow durch "*" markiert
 && adduser -D victim \
 && sed -i 's/^victim:[^:]*/victim:*/' /etc/shadow \
 # Passwort-Authentifizierung aktivieren, leere Passwörter verbieten
 && printf '%s\n' \
      'PasswordAuthentication yes' \
      'PermitEmptyPasswords no' \
   >> /etc/ssh/sshd_config

ENTRYPOINT ["/usr/sbin/sshd", "-D", "-e"]
```

Das Image basiert auf Alpine in Version 3.15. Deren `openssh-server`-Paket enthält den Fehler – ein bewusster Zustand für das Lab, zumal Alpine 3.15 seit Ende 2023 keine Updates mehr erhält.

Das Konto `alice` erhält ein echtes Passwort und dient später als Salt-Spender. Das Konto `victim` erhält kein Passwort; in `/etc/shadow` steht dafür ein `*`. Wichtig zur Einordnung: Ein `*` bedeutet nicht, dass das Konto prinzipiell unbrauchbar ist – der Login per SSH-Key bleibt möglich, nur die Passwort-Authentifizierung ist ausgeschlossen. Abschließend wird die Passwort-Authentifizierung in der sshd-Konfiguration aktiviert, während leere Passwörter weiterhin verboten bleiben.

Gebaut und gestartet wurde der Container mit:

```bash
docker build -t sshhole-lab .
docker run -d --name sshhole-lab -p 127.0.0.1:2222:22 sshhole-lab
```

Der Port wird bewusst nur an localhost gebunden – der Container ist angreifbar konfiguriert und gehört ausschließlich in eine gesicherte Lab-Umgebung. Vor dem Test lohnt ein Blick in die Shadow-Datei, ob der Salt-Spender korrekt angelegt wurde:

```bash
docker exec sshhole-lab grep alice /etc/shadow
```

Der Eintrag sollte mit `$6$` beginnen.

### Der Nachstellungsversuch

Zunächst der Plausibilitätscheck: Der Login als `alice` mit dem Passwort `correcthorse` funktioniert wie erwartet.

```bash
ssh -p 2222 alice@127.0.0.1
```

Der Login als `victim` mit einem kurzen Passwort schlägt hingegen fehl – so weit das erwartete Verhalten. Ändert sich das Bild mit einem Passwort von mehr als 256 Zeichen? Für den zweiten Versuch wurde ein String aus 300 mal dem Buchstaben `A` genutzt:

```text
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
```

Damit ist der Login tatsächlich möglich – allerdings erst im zweiten Versuch innerhalb derselben SSH-Verbindung. Beim ersten Prompt wird ein beliebiges falsches, kurzes Passwort eingegeben; erst wenn anschließend der lange String folgt, wird die Authentifizierung akzeptiert.

### Der Hintergrund

Der Grund für dieses Verhalten liegt in der Schnittmenge mehrerer Entscheidungen:

- Die `crypt()`-Funktion von musl implementiert sha512crypt mit einer maximalen Eingabelänge von 256 Bytes. Bei längeren Eingaben gibt sie den String `*` zurück – das ist kein Hash, sondern ein Fehlerindikator.
- In `/etc/shadow` steht genau dieses `*` auch für Konten ohne Passwort.
- Ein sshd ohne PAM vergleicht das Ergebnis von `crypt()` direkt mit dem gespeicherten Passwortfeld. Da ein `*`-Feld zu kurz für einen Salt ist, greift sshd auf den Salt eines anderen Kontos zu.
- Erhält sshd für ein überlanges Passwort nun `*` zurück und gleicht es mit dem gespeicherten `*` ab, gilt der Vergleich als erfolgreich – der Login wird akzeptiert.

Dass zwei Versuche nötig sind, hängt mit diesem Salt-Borrowing zusammen: Der erste Versuch füllt den internen Salt-Zwischenspeicher und leert dabei den Puffer, der den Shadow-Eintrag hält; erst beim zweiten Versuch bleibt das `*` erhalten und kollidiert mit dem Fehlerwert von `crypt()`.

### Was gibt es nun zu tun?

Betroffene Systeme sollten schnellstmöglich gepatcht werden. Wichtig und leicht zu übersehen: Nach dem Paket-Update muss sshd neu gestartet werden, da das Update allein den laufenden Daemon nicht ersetzt.

Ist ein Update kurzfristig nicht möglich, hilft als Übergang, eine der Grundvoraussetzungen zu entfernen – am einfachsten die Passwort-Authentifizierung:

```bash
echo 'PasswordAuthentication no' > /etc/ssh/sshd_config.d/00-no-passwords.conf
sshd -t && rc-service sshd restart
```

Bei SSH ist Key-basierte Authentifizierung ohnehin der empfehlenswerte Weg. In Containern lohnt zusätzlich die Frage, ob ein SSH-Login überhaupt notwendig ist – in den meisten Fällen ist die Antwort nein.

Wer prüfen möchte, ob ein System bereits angegriffen wurde, durchsucht die Logs nach `Accepted password for`-Einträgen für Konten, die kein Passwort besitzen sollten.

Wie auch bei dieser Schwachstelle zeigt sich die Wichtigkeit eines gepflegten Inventars: Wer Hardware, Software und genutzte Bibliotheken inventarisiert hat, kann sehr schnell prüfen, welche Komponenten im eigenen Netz tatsächlich betroffen sind – und muss nicht jede Meldung pauschal für die eigene Infrastruktur bewerten.

### Fazit

Die Nachstellung hat sich gelohnt: Die Schwachstelle ist real, aber die Bedingungen sind spezifisch – musl libc, kein PAM, ein Konto mit `*` und ein Konto mit passendem Hash als Salt-Spender. Genau diese Kette zu verstehen, hilft deutlich besser bei der Einschätzung des eigenen Umfelds als jede Schlagzeile. Das eigene Lab macht aus einer schnellen Meldung ein nachvollziehbares Bild – und genau das ist der Teil der Arbeit, der am meisten Learning gebracht hat.
